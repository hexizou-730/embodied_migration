# StackCube 自动修复与方法对照

日期：2026-10-23。任务 StackCube-v1，源机器人 Panda，目标 xarm6_robotiq，
目标控制模式 pd_ee_delta_pose。模型为 OpenRouter 上的 DeepSeek v4.1 Flash，
temperature=0，reasoning_effort=none，输出上限 6000 tokens。
环境、机器人控制器和官方成功标准保持不变。

## 自动局部修复：3 次分别运行

三次均从同一份此前失败的 LLM Adapter 开始，每次先 reset 并重放。
执行停止位置为 release；源端与目标端阶段状态比较发现，align 声称完成时，
目标端的官方 is_cubeA_on_cubeB 仍为 False。因此只开放 `_stage_align`。

新的修复请求只让 LLM 返回一个方法。Harness 按 AST 定位将其拼回原 Adapter，
再校验其它方法的语义哈希不变。Prompt 使用源阶段表示和实测状态，未提供人工成功
诊断代码。原始 prompt、LLM 方法输出、拼装代码和 trial 都保存在各次目录中。

| 运行 | LLM 采样 seed | 生成轮次 | 新候选累计 action | 成功候选 action | 官方成功 |
|---|---:|---:|---:|---:|---|
| r01 | 0 | 1 | 31 | 31 | True |
| r02 | 1 | 1 | 31 | 31 | True |
| r03 | 2 | 3 | 91 | 33 | True |

环境 seed 始终为 0。3/3 是三个分别发起的修复运行，不是三个不同场景的成功率。
三份最终 Adapter 的 SHA-256 均不同，且与原代码比较都只修改 `_stage_align`。
第三次的两个失败候选（各 29 actions）均保留，没有删除。
三次修复合计调用 5 次 LLM、使用 22,188 tokens、记录费用 $0.002445942；
此外每次均重放了 101 actions 的初始候选，不计入上表“新候选累计 action”。
它们是已有候选续修，不能混入从零生成实验。

结果目录：`results/selective_migration/method_patch_r01` 至 `method_patch_r03`。

## 对照定义

输入审计说明：`corrected_comparison` 是纠正夹爪接口后的探索组，但其首轮提示完整
序列化了源阶段文件，附带了人工验收标签。它没有获得人工目标代码，物理结果保留，
但不作为净输入主对照。后续 `source_facts_comparison` 明确过滤 validation 和
input_evidence 元数据，仅提供提取到的源事实；下文最终结果采用这组数据。
三次已有候选单方法修复只读取对应阶段，未序列化顶层验收标签，不受此问题影响。

三种方法每次从零生成，不共享成功目标代码。每个方法最多三轮生成，
统一目标接口、模型、物理场景、最大 episode 步数（1000）及输出 token 上限（6000）。
每轮可见的输入内容及输出粒度是方法差异，所以输入 token 总量并非相同。

| 方法 | 源端信息 | 输出与修复范围 |
|---|---|---|
| target_only | 任务定义与目标接口，无源代码/轨迹 | 整体生成，失败后整体重写 |
| whole_rewrite | 源代码及源阶段表示，含阶段末状态 | 整体生成，失败后整体重写 |
| selective | 源阶段表示，含阶段末状态 | 首轮完整生成；后续只生成诊断指定的方法 |

每种方法分别运行三次，LLM 采样 seed 为 0、1、2，环境 seed 固定为 0。
全部失败运行计入结果；接口或 API 故障另列，不能以生成代码或到达 TCP 位置代替
官方成功。整体方法还获得了完整源代码，因此此对照评价整套方法，不能只把差异
归因于“输出一个方法”这一项；该项的独立作用仍需后续消融。

## 从零生成的主对照结果

`source_facts_comparison` 已完成全部 9 个运行，没有 API 基础设施失败。
下表是每种方法三次运行的总消耗，包含失败候选，不是只统计成功代码。

| 方法 | 官方成功 | LLM 调用 | 累计 action | 累计 tokens | 记录费用（美元） |
|---|---:|---:|---:|---:|---:|
| target_only | 2/3 | 9 | 975 | 84,283 | 0.01185703 |
| whole_rewrite | 2/3 | 7 | 1,329 | 96,957 | 0.01192033 |
| selective | 2/3 | 8 | 366 | 50,325 | 0.00613844 |

三组逐次结果：

| LLM 采样 seed | target_only | whole_rewrite | selective |
|---:|---|---|---|
| 0 | 成功 | 失败 | 失败 |
| 1 | 失败 | 成功 | 成功 |
| 2 | 成功 | 成功 | 成功 |

观察：本组成功数相同，selective 消耗的 action 和 tokens 更少；生成轮数并非最少。
这是整套方法的探索性结果，不证明局部修复具有统计显著优势，也不证明源程序一定
有帮助。场景只有一个，独立生成只有三次，且各方法的信息量不同。
本次允许 OpenRouter provider fallback，实际供应商随请求变化；原始 usage 保留该信息。
temperature=0 和采样 seed 不保证跨供应商返回完全一致的代码。

失败并没有消失：target_only 的失败运行连续三轮未建立有效接触；whole_rewrite 的
失败运行先后遇到接触失败、numpy 数组布尔判断异常和 1000 步预算耗尽；selective
的失败运行三轮都停在 align。另有一次整体重写返回相同代码，被检查器拒绝，仍计入
生成次数。这些限制不能用“流程已跑通”来替代。

审计前的 `corrected_comparison` 为 1/3、3/3、2/3，仅作为探索记录保留，不与主组
合并或择优报告。两组结果变化不能单独归因于删除验收标签，供应商和生成波动也未隔离。

## 阶段判断与下一步

本轮完成的目标：自动生成真实动作、根据测量定位上游阶段、只重写一个方法，
并以官方成功和三方法对照验收。人工成功代码没有作为自动修复的答案输入。
当前可以说“局部修复可行，并在本组减少了执行与文本消耗”，不能说“成功率更高”。

暂不扩展 20 个任务，不追加同场景调参。后续最小实验应从同一失败候选出发，
只改变“整体重写/单方法修复”，使用相同状态反馈和预算，以隔离修复粒度的作用；
再把固定代码放到未参与修复的新场景。没有优势就保留负结果，不继续加模块。

## 复核

`python evidence/stackcube_automatic_20261023/verify.py` 离线重算主组汇总，检查官方
成功、真实动作、局部修改范围与人工验收标签隔离，不调用 LLM 或仿真。
`verification.json` 记录检查结果；`verified_summary.json` 是派生汇总，原始 trial、
prompt、LLM 输出和执行时 summary 不覆盖。执行框架快照分别保存在
`executed_runtime/`（审计前）和 `executed_runtime_source_facts/`（主组）。
本地验收：56 项证据检查通过，主组共保存 24 份生成提示；112 项测试通过。
